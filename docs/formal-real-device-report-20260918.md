# sing-box 入站正式真机横评报告

- 测试日期：2026-09-18
- 测试矩阵：`pkx110-formal-core-v6-20260918`
- 测试分支：`ebpf-inbound`
- 报告性质：Android 真机、Wi‑Fi 局域网、单设备 local 数据面正式横评

## 1. 测试环境

- 设备：Android 16，`aarch64`
- 内核：`6.6.118-android15-8-g93e223c276e7-abogki500782043-4k`
- 网络：Wi‑Fi 局域网，测试目标 `10.212.17.63:19090`
- 屏幕：关闭
- 移动数据：关闭
- 测试过程中停止生产 sing-box，测试结束后恢复
- eBPF 测试覆盖 local TC 与 local cgroup 两种数据面

本次不包含 shared/hybrid 热点多设备测试，也不包含 IPv6 专项、网络切换和长时间待机耗电测试。

## 2. 测试规模与统计口径

- 83 个测试 case
- 340 个 job
- 每个 case：1 次 warm-up + 3 次正式重复
- 所有 340 个 job 均完成
- 未发现传输损坏、结果格式错误或清理失败导致的无效 job
- UDP recovery 探测共 84 次：83 次首轮恢复成功，1 次第二轮恢复成功
- 第 1 个 raw throughput control block 出现 11.10% 漂移，超过 5% 有效性阈值，因此该 block 的正式测量被排除
- 最终汇总每个 case 使用 2 次有效正式重复的中位数
- CPU 单位为逻辑 CPU core 占用；PSS 为进程 PSS；BPF map 为独立的 memlock/map 统计
- UDP PPS 与 Mbit/s 只使用 active offered-load 窗口，收尾 drain 时间不重复计入吞吐损失
- `Success %` 的分母包含成功操作、failed 和 lost

## 3. 覆盖的入站方案

- `raw`
- `direct`
- `redirect`
- `tproxy`
- `tun`
- `tun-auto-redirect`
- `ebpf-tc`
- `ebpf-cgroup`

负载包括 standby、TCP RTT、TCP 长流上传/下载、TCP short、TCP idle、UDP connected/unconnected RTT、UDP PPS 和 UDP MTU。`redirect` 不生成 UDP case，因为该方案的 UDP 能力不适用。

## 4. 关键结论

1. eBPF TC 在 TCP 长流、UDP PPS 和 MTU 测试中整体接近或达到传统方案水平。
2. eBPF TC 的 standby 进程 PSS 为 45.70 MiB，较 direct 高约 4.65 MiB，BPF map 约 1.83 MiB。
3. eBPF cgroup 的 standby 进程 PSS 为 45.20 MiB，较 direct 高约 4.15 MiB，BPF map 约 1.76 MiB。
4. eBPF TC UDP PPS 为 1993.95 ops/s、成功率 99.697%；UDP MTU 为 500.07 PPS，基本达到目标负载。
5. eBPF cgroup UDP PPS 为 1972.00 ops/s、成功率 98.607%；UDP MTU 为 498.42 PPS，未发现数据完整性问题。
6. eBPF cgroup 的 TCP short 汇总曾出现 227.99 ops/s、p95 约 1108.8 ms；复核原始样本后，异常只存在于一个 repetition 的首轮 32 个连接，下一轮 32 个连接立即恢复到 47–54 ms。后续同机复测未复现，因此不能据此认定为稳定的 cgroup 数据面缺陷。
7. 本轮没有发现 eBPF TC/cgroup 导致的普遍 UDP 丢包、MTU 损坏、资源泄漏或恢复失败。
8. 本轮结果不能替代 shared/hybrid、IPv6、网络切换、多设备热点和长时间待机耗电验证。

## 6. 详细延迟结果

### 6.1 eBPF cgroup TCP short 复核

异常 case 的三次有效正式重复中，两次完全正常，最大延迟约 85–90 ms；仅一次耗时约
1.17 秒。该异常 repetition 共 64 次操作、32 个 worker，每个 worker 各执行两次：

- 32 个 worker 的第一次连接全部为 1089–1112 ms；
- 同一批 worker 的第二次连接全部为 47–54 ms；
- 成功率仍为 100%。

这种“整个首轮同时多出约一秒，随后立即恢复”的分布更接近 TCP 初始 SYN 重传、Wi‑Fi
省电/调度或服务端/链路的整批停顿，不符合 eBPF map 查询、token 冲突或
`TakeOriginal` 等逐连接成本的常见形态。本轮其他 case 也出现过 TUN UDP RTT 约 3.95 秒、
direct UDP RTT 约 2.91 秒的瞬时异常，说明测试链路存在短时波动。

2026-09-18 在同一设备重新运行 cgroup TCP short（32 并发、每轮 128 次、连续 5 轮），
成功率均为 100%，吞吐为 415.7–523.5 ops/s，中位数 468.36 ops/s；汇总 p50/p95/p99 为
60.86/102.77/111.25 ms，各轮最大值为 86–128 ms，未复现一秒级尾延迟。

因此本报告保留原始测量值，但将结论降级为“观测到一次尚未归因的首轮整批停顿”。当时的
工具尚未拆分 connect/application 延迟，也未采集 SYN 重传计数，无法对历史样本做进一步
确定性归因。

## 9. 本轮实机测试推动的 bench 修复

- TCP short 单连接传输失败不再中止整轮测试，而是继续固定尝试数并记录 `failed`。
- TCP idle 部分连接建立失败时保留成功连接并报告成功率。
- 路径证明预热最多使用 8 个连接/flow，避免使用 250 个 idle 并发连接自我施压。
- raw 路径证明允许同源 IP 下源端口改写，避免 conntrack/NAT 端口冲突造成误判。
- 新增 `--requests`，可复现地控制 RTT/TCP short 请求数，不影响 UDP churn。
- TCP short 新增总耗时、connect 耗时与 application 回显耗时三组同序样本。
- Linux/Android 测量窗口新增 TCP/SYN 重传、超时与 listen overflow/drop 主机计数器；
  汇总明确其可能包含后台流量，仅用于结合分阶段延迟判断。
- 汇总新增 `Success %`，分母包含 `operations + failed + lost`。
- UDP PPS 的 Ops/s/Mbit/s 改用 active offered-load 窗口，不再把 drain 等待重复算成吞吐损失。
- TCP server 将 idle 空连接的 clean EOF 视为正常关闭，避免约 1.1 万行日志污染。

## 11. 后续建议

1. 若再次出现 TCP short 秒级尾延迟，先用新版分阶段延迟和 TCP 计数判断停顿发生在 connect 还是 application；只有 hook 到 accept/dispatch 阶段被证实后，才修改 cgroup 数据面。
2. 使用 perf/tracepoint/BPF counters 拆分 softirq、TC、netfilter、路由与 sing-box 用户态 CPU，避免只依据 PID CPU 判断功耗。
3. 增加 shared/hybrid 热点、多设备并发、IPv6、网络切换和长时间 standby 测试。
4. 对 UDP flow churn、map occupancy、release 事件和恢复重挂载做长时间压力测试。
5. 在另一台 Android 内核版本（尤其 4.19/5.4 厂商内核）上复测能力探测、attach、UDP hook 和 TC 共存行为。
